# 탐지 규칙

모든 규칙은 Groth16 검증키(α, β, γ, δ, IC)를 대상으로 한다. 검증키는 검증된 소스에서 뽑고(`scanner/extract.ts`),
소스가 없으면 바이트코드에서 판정한다(`scanner/bytecode.ts`).

## 배경: snarkjs 셋업

- Phase 1(powers of tau)에서 α, β가 정해진다. 같은 ptau 파일을 쓴 회로는 α, β가 같다. 정상이다.
- `groth16 setup`은 γ와 δ를 둘 다 G2 생성원으로 둔다.
- Phase 2(회로별 기여)에서 δ만 무작위화한다. γ는 생성원으로 남는다.

그래서 "γ == 생성원"은 정상이고 규칙이 될 수 없다. 단계 0 벡터로 확인하면 이 조건은 음성 11개를 전부 오탐으로 잡는다 (L01).

## R1: γ == δ (치명)

γ와 δ가 같으면 검증 방정식에서 두 항이 합쳐져, 증명의 건전성이 깨진다. Phase 2를 건너뛴 snarkjs 검증기가
대표적이고(γ == δ == 생성원), 2026년 2월 Veil·Foom 사고의 원인이다.

- 소스: 추출한 γ와 δ를 비교한다.
- 바이트코드: 템플릿은 β·γ·δ를 연달아 넣으므로, 상수 열에서 "β → X → X"(같은 G2 점이 연달아 두 번)를 찾는다.
  소스 판정 867개(다섯 체인) 대비 오탐 0, 놓침 0.

## R2: δ == G2 생성원 (치명)

Phase 2 기여가 한 번도 없었다는 뜻이다. snarkjs에서는 R1과 함께 걸린다.

## R3: 같은 δ가 서로 다른 회로의 검증기에서 재사용됨 (정보)

회로마다 Phase 2 기여를 따로 했다면 δ는 회로마다 다르다. 서로 다른 회로가 같은 δ를 쓰면 같은 기여를 재사용했다는 뜻이다.
한 회로의 δ 비밀이 새면 다른 회로도 함께 깨진다. 비컨만으로 만든 기여(비밀 기여 없음)를 여러 회로에 같은 값으로 쓰면
이렇게 되는데, 그 경우 δ는 누구나 계산할 수 있다.

- 같은 회로를 여러 번(여러 체인에) 배포해 δ가 같은 것은 정상이다. 회로는 α와 IC 점으로 구분한다.
  회로가 다르면 IC가 전부 달라 α 하나만 겹치므로, G1 점이 두 개 이상 겹치면 같은 회로로 묶는다.
- δ가 생성원인 경우는 R1·R2가 다루므로 R3에서 뺀다.
- 합성 phase2 벡터 두 회로는 같은 비컨 값으로 만들어 R3에 걸린다. 테스트가 이것을 기대한다.

## R4: 공개 입력에 스칼라 필드 범위 검사가 없음 (후보)

아직 구현하지 않았다. snarkjs 템플릿은 신형(`checkField`)·구형(`snark_scalar_field`) 모두 검증기 안에서 범위를 검사하므로,
템플릿 검증기 자체보다는 검증기를 호출하는 쪽(nullifier 처리 등)을 봐야 한다.

## 바이트코드 판정

| 판정 | 조건 | 뜻 |
| --- | --- | --- |
| detected | "β → X → X" 연속 패턴 | R1 |
| suspect | 패턴은 없고, 생성원과 다른 G2 점이 하나뿐 (생성원 좌표가 데이터 영역에만 있어도 포함) | 옵티마이저가 같은 상수를 합쳤거나(L15) CODECOPY로 옮긴(L33) 결함일 수 있고, δ가 상수로 박혀 있지 않은 정상 검증기일 수도 있음. 사람이 확인 |
| clean | 서로 다른 G2 점 3개 이상 | β, γ, δ가 모두 다름 |
| not-groth16 | 그 밖 | |

한 컨트랙트에 검증키가 여러 개면 그중 하나의 결함을 놓칠 수 있다.
